Executive Summary

AXIS Bank requires 160+ disks per VM. We tested pre-attached disks (defined in the VM spec, not hot-plugged) across multiple disk counts and bus types to validate this requirement and find the upper limit.

AXIS Bank Requirement: Validated

  • 160 virtio disks: All 5 validations PASS, 13 min total (Build #208)
  • 200 SCSI disks: All 5 validations PASS, 14 min total (Build #211)
  • Guest OS confirms all disks visible via lsblk and SSH validation

Finding: Virtio Bus Limit at ~170 Disks

Above ~170 virtio-blk disks, the guest network adapter fails to register due to MSI-X interrupt vector exhaustion. The fix is to use bus: scsi (virtio-scsi controller) instead of bus: virtio for data disks. This is a known architectural constraint, not a bug. See Root Cause Analysis below.

  • 160 disks: ~8.4 min VM Ready - ~18x increase, mainly PVC binding and volume attachment
  • 200 disks: ~9.7 min VM Ready - ~21x increase, CSI attacher handles 200 volumes with transient FailedAttachVolume events (all eventually succeed)

Root Cause Analysis: Virtio vs SCSI

The Problem

With 200 virtio-blk disks, the VM boots but has no network connectivity. SSH validation fails on every attempt. The Guest OS shows only lo (loopback) - no eth0 or enp1s0.

Root Cause

MSI-X Interrupt Vector Exhaustion

Each bus: virtio disk gets its own PCI device with its own MSI-X interrupt vectors. With 200+ virtio-blk devices consuming all available vectors, the virtio-net NIC fails to claim its interrupt resources during guest kernel initialization. The NIC driver silently fails to probe, leaving the VM with no network.

This is not a bug - it is an architectural limitation of the virtio-blk transport. Alexander Wels (HCP team) confirmed this in the original email thread: "It requires a SCSI controller, otherwise you are limited by the number of PCIe slots."

The Fix

Switch Data Disks to bus: scsi

A single virtio-scsi controller occupies one PCI slot and multiplexes hundreds of disks behind it. The NIC retains its PCI resources and registers normally.

CSI Attacher Behavior at Scale

With 160-200 PVCs, the Ceph RBD CSI external-attacher produces transient FailedAttachVolume events. These are retried automatically by kubelet and all volumes eventually attach successfully.

Disk CountFailedAttachVolume EventsFinal Attach Status
100All attached
160~5All attached (after retry)
180~25All attached (after retry)
200~49All attached (after retry)
The FailedAttachVolume events are transient. The CSI attacher retries, and all volumes eventually attach. The VM boots with all disks. This is expected behavior when requesting many concurrent volume attachments from a single Ceph cluster.

Key Takeaways

  • AXIS Bank's 160-disk requirement is validated - works with both virtio (160) and SCSI (200) bus types
  • SCSI bus is required above ~170 disks - virtio-blk exhausts MSI-X interrupt vectors, causing guest NIC failure
  • 200 SCSI disks works with all validations - VM boots in ~9.7 min, all disks visible in guest OS via lsblk
  • Boot time scales linearly - 46s for 10 disks, ~8.4 min for 160, ~9.7 min for 200 (PVC binding is the bottleneck)
  • CSI attacher handles 200 volumes - transient FailedAttachVolume events at scale, but all volumes eventually attach
  • Hot-plug test (255 disks) also passes - the existing regression suite validates 255 hot-plugged SCSI disks with persistence
