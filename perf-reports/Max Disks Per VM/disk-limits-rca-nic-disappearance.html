Executive Summary

The guest NIC disappears at 177+ virtio-blk data disks because the MSI-X interrupt vector pool is exhausted by disk devices before the virtio-net driver can probe. Each virtio-blk disk consumes its own dedicated PCIe root port (1 PME MSI-X vector) plus 17 device MSI-X vectors (1 config + 16 multiqueue request queues for 16 vCPUs), totaling 18 interrupt vectors per disk.

The virtio-net driver loads after virtio-blk (which is required for boot), and when it finally probes, it cannot allocate even the minimum 2 MSI-X vectors. Since virtio-non-transitional devices require MSI-X (no legacy INT#x fallback), the NIC probe fails completely and no network interface is created.

Root Cause: MSI-X Interrupt Vector Exhaustion

Each bus: virtio disk gets its own PCI device with 17 MSI-X vectors + 1 PCIe root port PME vector = 18 total. At 177 disks, the ~3,200 vector pool is exhausted. The NIC probes last and gets zero vectors.

Fix: Switch Data Disks to bus: scsi

A single virtio-scsi controller occupies one PCI slot (~19 vectors) and multiplexes hundreds of disks behind it. The NIC retains full resources. Proven working with 200+ disks.

Exact Breaking Point

The NIC completely fails at 177 data disks (virtio-blk bus).

Degradation Timeline

  • At 170 data disks: NIC still gets full 33 vectors (16 RX/TX queue pairs)
  • At 175 data disks: NIC falls to 2 vectors (single-queue fallback) - degraded
  • At 176 data disks: NIC gets 2 MSI-X vectors (minimum viable - single queue mode) - degraded
  • At 177 data disks: NIC gets 0 MSI-X vectors (probe fails, no network interface) - FAILED

QEMU/PCI Topology Analysis

180-disk (virtio-blk) topology

  • 382 PCIe root ports on bus 0 (slots 0x02-0x19, multifunction)
  • 190 root ports actively used (each consuming 1 PME MSI-X vector)
  • NIC at bus=0x01, slot=0x00 (always first secondary bus)
  • Disks on buses 0x07 through 0xBC (182 virtio-blk devices: 180 data + root + cloudinit)
  • Each disk gets its own PCIe root port and dedicated PCI bus

200-disk (SCSI) topology

  • 32 PCIe root ports only
  • NIC at bus=0x01, slot=0x00 (same)
  • ALL 200 data disks behind a single virtio-scsi controller (controller='0')
  • One PCI device serves all 200 disks

Why SCSI Fixes It

With bus: scsi, KubeVirt creates a single virtio-scsi controller (type virtio-non-transitional). All data disks are LUNs behind this one controller.

Root Cause Chain (Definitive)

1. KubeVirt allocates one PCIe root port per virtio-blk disk
       |
2. Each disk's driver requests 17 MSI-X vectors (1 config + num_cpus queues)
       |
3. Each root port consumes 1 additional PME MSI-X vector
       |
4. Total = 18 vectors per disk x N disks = exhausts interrupt pool at N ~ 177
       |
5. virtio-blk probes BEFORE virtio-net (boot dependency ordering)
       |
6. virtio-net probes last, calls pci_alloc_irq_vectors() -> FAILS
       |
7. virtio-non-transitional has no legacy INT#x fallback -> probe() fails
       |
8. No net_device registered -> no enp1s0 -> VM has no network

Recommendations

For KubeVirt Project

  • Validation webhook: Reject VM specs with > 170 virtio-blk disks (or warn above 160) when using a multiqueue NIC
  • Auto-switch to SCSI above threshold: When disk count exceeds ~150, automatically use a virtio-scsi controller instead of individual virtio-blk devices. This is the approach used by VMware and Hyper-V.
  • Document the limit: The effective maximum is (MSI-X_ceiling - NIC_vectors - overhead) / 18. With 16 vCPUs and a 16-queue NIC, this works out to ~170-176 disks.
  • Consider disk multiqueue tuning: Each disk requests num_possible_cpus queues. A single-queue mode per disk (queues=1) would reduce vectors from 17 to 2 per disk, allowing ~1,500 disks before exhaustion.

For Immediate Use

  • Use bus: scsi for data disks when disk count exceeds 100. This is the proven fix.
  • The root disk and cloudinit can remain virtio-blk (only 2 devices, minimal overhead).
  • SCSI performance is comparable to virtio-blk for the workloads tested.

Key Takeaways

  • Not a KubeVirt bug - fundamental consequence of PCIe topology: every virtio-blk disk is an independent PCIe endpoint device
  • Hard limit: 176 virtio-blk data disks (NIC degraded but functional) or 170 disks (NIC at full performance) for a 16-vCPU VM
  • SCSI has no such limit - all disks share one PCIe device, vector usage stays at ~141 regardless of disk count
  • Degradation is progressive - NIC loses queues before failing entirely (175 = degraded, 177 = dead)
  • Other devices also affected - serial console fails at 180 disks, last few disks degrade to single-queue

Conclusion

This is NOT a KubeVirt bug per se, but a fundamental consequence of the PCIe topology: every virtio-blk disk is an independent PCIe endpoint device. The practical limit for a 16-vCPU VM with a 16-queue NIC is 176 virtio-blk data disks (NIC degraded but functional) or 170 virtio-blk data disks (NIC at full performance). The fix is to use virtio-scsi for high disk counts, which has no such limit since all disks share one PCIe device.
