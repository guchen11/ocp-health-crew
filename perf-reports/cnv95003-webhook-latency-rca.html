CNV-95003: CDI Webhook Latency - Root Cause Analysis

VM creation regression traced to controller-runtime overhead in the CDI API server

Root Cause Identified: CDI API Server Overloaded
Controller-runtime engine added in CDI v1.59 (CNV 4.21) inside a single-replica pod with 100m CPU

TL;DR

The cdi-apiserver was designed as a lightweight webhook handler. In CDI v1.59 (CNV 4.21), two PRs (#2813, #3029) added a full controller-runtime engine (informers, caches, field indexers) inside this same single-replica pod running on only 100m CPU. The background work now competes with webhook handling for CPU.

One root cause, two symptoms:

  • Single VM: Every webhook call pays additional overhead from CPU contention with background work, even with no other load.
  • At scale (100+ VMs): ~30-50% slower overall, up to 19x at P99. Concurrent webhook requests queue up on the single-replica pod. This matches the original CNV-95003 report.

Key insight: The webhook itself is fast (~125ms). The 2.4s P99 latency is entirely caused by requests queuing on a single-replica pod. This is why even a single VM sees 30-50% regression - the background controller-runtime work steals CPU cycles from the webhook handler.

Why didn't 2 replicas cut time in half?

The early ramp-up improved 4x (28 VMs at 60s vs 7). But the CDI controller (cdi-deployment, also single-replica with 100m CPU) becomes the next bottleneck once webhooks are faster. The full pipeline has two serialization points: webhook admission and controller reconciliation.

Source Code Analysis: CDI v1.57 vs v1.60

Compared upstream kubevirt/containerized-data-importer between v1.57.1 (CNV 4.19) and v1.60.5 (CNV 4.22).

CDI v1.57 (CNV 4.19) - Before

  • Lightweight HTTP server
  • Direct k8s API clients only
  • No informers, no caches
  • No field indexes
  • Webhook-only process

CDI v1.59+ (CNV 4.21+) - After

  • Full controller-runtime/cluster
  • Informers for CoreV1, CDI, Snapshots
  • In-memory caches that must sync
  • PV field indexers
  • New PVC mutating webhook
  • Feature gate checks on every validate call

The Two PRs That Caused the Regression

PRTitleImpactFirst Release
#2813 Add PVC spec mutating webhook rendering based on StorageProfiles Added cluster.New() + cluster.Start(), field indexers, new PVC webhook v1.59.0
#3029 Feature Gate and annotation for PVCs to be adopted by DataVolumes Added ClaimMayExistBeforeDataVolume() - reads CDIConfig on every validation v1.59.0
Note: The validate webhook actually performs fewer direct API calls in v1.60 than v1.57 (PR #3331 removed source PVC/snapshot validation from the webhook). However, the infrastructure overhead of the embedded controller-runtime cluster more than offsets this improvement.

Recommended Fixes

1. Make CDI API server replicas configurable

Currently hardcoded to 1 by the CDI operator. Our test showed 2 replicas halved the P50 webhook latency and gave 4x more VMs running at 60s. This is the lowest-effort, highest-impact fix.

2. Increase default CPU request

100m is insufficient for a process running controller-runtime alongside webhook handlers. Increase to at least 500m, or add an HPA that scales based on webhook request rate.

3. Decouple controller-runtime from the webhook server

Move the controller-runtime cluster out of the API server process entirely, or lazy-load it only when the WebhookPvcRendering feature gate is enabled. The API server should return to being a lean webhook handler.
