CNV-95003: VM Creation Performance - Root Cause Analysis

Investigation into VM creation regression between OCP 4.19 and OCP 4.22

CDI Code Ruled Out as Cause
CDI v1.58 and v1.60 perform identically on the same cluster. The 30-50% regression reported between OCP 4.19 and 4.22 originates outside CDI.

TL;DR

CDI's multi-step DataVolume pipeline adds ~100s overhead vs direct PVC creation at 100-VM scale. However, this overhead is not a regression - it is identical between CDI v1.58 (CNV 4.19 era) and v1.60 (CNV 4.22). We proved this by swapping both the cdi-apiserver and cdi-deployment to v1.58.5 upstream images on the same 4.22 cluster.

The 30-50% regression Purti reported between OCP 4.19 and 4.22 likely originates from infrastructure changes in the broader stack (API server, etcd, ODF/CSI driver, Kubernetes version). Confirming this requires a comparison test on an OCP 4.19 cluster.

Conclusion: All CDI versions produce the same ~160s result. The CDI code did not regress between v1.57 and v1.60. The ~100s overhead vs direct PVC creation is CDI's inherent architectural cost (multi-controller reconciliation, 3-worker concurrency, multi-step pipeline), and has been present since at least CDI v1.57.

Disproved Hypothesis: CDI Webhook PRs

Initially suspected: PRs #2813 and #3029 in CDI v1.59

Our initial analysis identified two PRs that added a controller-runtime cluster inside the cdi-apiserver. We hypothesized this caused webhook latency to increase. However, swapping the cdi-apiserver to v1.58.5 (before those PRs) produced identical webhook latency (P99 ~2.48s vs ~2.45s). The high webhook latency is caused by request queuing on the single-replica pod, not by the webhook code itself.

Where the CDI Time Goes

CDI's DataVolume snapshot clone pipeline has multiple serialization points. These are architectural, not version-specific.

StageBottleneckMeasured
Webhook admission (mutate + validate)Single-replica cdi-apiserver queues requestsP99: ~2.5s under load (same in v1.58 and v1.60)
Controller reconciliationdatavolume-snapshot-clone-controller - 3 workersQueue wait: 6.8s avg, work: 0.37s per item
Reconcile churn~80 reconciles per DV across multiple controllers8116 total adds for 100 DVs
CDI controller config1 replica, 100m CPU, 353Mi memory used2 reconciles/sec at peak

Why is CDI slow?

A DataVolume goes through multiple controllers (snapshot-clone, clone-populator, import-controller, upload-controller, clone-controller), each watching PVC events. Every PVC change triggers reconciliation across all controllers, most of which discard the event after checking annotations. With 3 workers and ~80 reconciles per DV, the queue backs up. This is CDI's design - not a regression.

Next Steps

To identify the actual regression source, a comparison test on an OCP 4.19 cluster with the same hardware profile is needed. The test should use the same kube-burner scenario (100 VMs, DV snapshot clone) and collect Prometheus metrics for webhook latency, controller queue depth, and CSI operation timing.

CDI Architectural Improvement Opportunities

While CDI code did not regress, its architecture has inherent scale limitations that are worth addressing.

1. Increase MaxConcurrentReconciles for snapshot-clone controller

Currently hardcoded to 3. With 6.8s average queue wait, increasing to 10-15 workers would significantly reduce wait time at scale.

2. Reduce reconcile churn

~80 reconciles per DV is excessive. Most are discarded by controllers that don't own the PVC type. Adding stricter event filters (predicates) would reduce unnecessary work.

3. Make CDI controller replicas and CPU configurable

Both cdi-apiserver and cdi-deployment run as single replicas with 100m CPU. Allowing operators to scale these based on workload would help at scale.
