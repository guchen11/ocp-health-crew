Why CDI is Slow

CDI Path (47h 30m for 10K)

  1. VM controller creates DataVolume
  2. CDI detects DV, creates temp VolumeSnapshot
  3. CDI polls snapshot readiness (~5s intervals)
  4. CDI creates target PVC from snapshot
  5. CDI polls PVC status (~5s intervals)
  6. CDI updates DV status (4-6 PATCH calls)
  7. CDI cleans up temp snapshot
  8. VM controller detects DV=Succeeded, VMI boots

Steps 2-7: single CDI controller pod, ~12-16 API calls per DV, processed one at a time. 50 DVs = 600-800 sequential API calls.

PVC Bypass (5h 25m for 10K)

  1. Create VolumeSnapshot from golden image (once)
  2. Bulk create 50 PVCs from snapshot (one oc apply)
  3. Bulk create 50 VMs with persistentVolumeClaim (one oc apply)
  4. VMIs scheduled and boot

CDI completely bypassed. CSI driver clones directly with Ceph in parallel. 2 API calls per batch regardless of scale.

VM Scheduling Spikes

Approximately 1 in 7 batches shows a VM startup time of 110-170s instead of the typical 38-50s. These occur roughly every 7 batches across the entire run and are periodic, not correlated with VM count. They appear to be caused by the virt-controller processing a burst of VirtualMachine objects. PVC creation is never affected by these spikes.

Recommendations

1. Adopt PVC bypass as the standard pattern for scale testing

The evidence is conclusive: PVC bypass eliminates the provisioning bottleneck at all scales. For any future VM scale test, pre-create PVCs from VolumeSnapshot instead of using DataVolume templates. The one-time setup (108s) is negligible compared to the 8.8x overall runtime improvement.

2. Report CDI bottleneck findings to the CNV team

The single CDI controller pod is the root cause of VM provisioning degradation at scale. This impacts production workloads that use DataVolume. Key recommendations for CDI:

  • Increase CDI controller worker concurrency
  • Shard CDI controllers (per-namespace or hash-based)
  • Optimize DV status reconciliation loop at high object counts
  • Consider direct CSI snapshot clone path for simple clone operations

3. Extend to 20K+ VMs if needed

Based on the flat performance curve and healthy cluster metrics at 10K (etcd 1.2GB, CSI 1.1Gi, Ceph healthy), there is significant headroom to push higher. The cluster has 39 workers, 21 OSDs, and 58 TiB storage. The PVC bypass approach should scale linearly until node resources (CPU/memory for virt-launcher pods) become the limiting factor.
