CDI vs PVC Bypass: Clone Mechanism Proof

Proving that both paths use the same Ceph thin clone - the difference is purely CDI orchestration overhead

Key Finding
Both CDI and PVC bypass produce identical Ceph RBD thin clones. The golden image is imported exactly once. All subsequent VMs are copy-on-write clones with zero additional data transfer. The 16.7x performance difference at 10K scale is entirely due to CDI's single-controller sequential processing overhead.

Why CDI Is Slower: The Design Issue

PVC Bypass Path

  1. oc apply creates 5 PVCs with dataSource: VolumeSnapshot
  2. CSI provisioner picks them up in parallel
  3. Each tells Ceph: "create thin clone from snapshot" (metadata op)
  4. All 5 bound within seconds

Total API calls: 5 CREATE (one per PVC)

CDI Path (per DataVolume)

  1. CDI controller detects new DV (LIST/WATCH)
  2. Creates temporary VolumeSnapshot from source PVC (CREATE)
  3. Polls snapshot readiness (GET x 2-3)
  4. Creates target PVC from temp snapshot (CREATE)
  5. Polls PVC status (GET x 2-3)
  6. Updates DV status multiple times (PATCH x 3-4)
  7. Deletes temporary snapshot (DELETE)
  8. Final DV status update (PATCH)

Total API calls: ~12-16 per DV, processed sequentially

Impact at Scale

ScaleCDI Batch TimeBypass Batch TimeCDI Overhead
5 VMs (this test)~5s~30s (includes Ceph clone)Minimal (idle cluster)
1,000 VMs181s74s2.4x slower
5,000 VMs~936s80s11.7x slower
10,000 VMs1,388s83s16.7x slower
Why it gets worse at scale: As total object count grows in the cluster, CDI's LIST/WATCH cycles take longer, API server PATCH calls take longer, and etcd queries slow down. The bypass doesn't suffer from this because it makes only 1 API call per PVC and lets CSI handle the rest directly with Ceph.

Scenarios That Force CDI (No Bypass Available)

ScenarioWhy CDI Is Required
MTV (VMware/RHV migration)CDI handles disk import from external sources (VDDK, NBD)
Cross-namespace cloningVolumeSnapshot is namespace-scoped, CDI bridges namespaces
Image import from URLOnly CDI can pull qcow2/raw from HTTP/S3
virtctl image-uploadCDI's upload proxy handles the streaming
Disk resize during cloneCDI handles expansion as part of the clone
This matters beyond testing: Customers using MTV to migrate thousands of VMs from VMware will hit the same single-controller bottleneck. CDI needs either controller sharding, increased worker concurrency, or a fast path for simple snapshot clone operations.

CDI uses 6x more API calls than bypass for the same 5 clones. At scale, each of those calls takes longer because the API server and etcd have more objects to process - this is the compounding effect that causes batch time to grow from 181s to 1,388s.

Prometheus Query

sum by (verb, resource) (
  increase(apiserver_request_total{
    resource=~"datavolumes|volumesnapshots|persistentvolumeclaims|volumesnapshotcontents"
  }[2m])
)

Run this in OpenShift Console > Observe > Metrics while creating DataVolumes or PVCs.

How to Monitor API Calls Manually

Option 1: Prometheus UI (Visual)

  1. Open OpenShift Console > Observe > Metrics
  2. Enter the query above
  3. In another terminal, create a DataVolume or PVC
  4. Watch the graph - you'll see spikes on PATCH (DV status updates), GET (polling), POST (creating PVCs/snapshots), DELETE (cleanup)
  5. Refresh every 30s to see counts climb
