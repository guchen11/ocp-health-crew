API Server / Scheduler Degradation Analysis - 10K VM Test

Root Cause Analysis and Projection Model

Degradation Analysis Report
10,000 VM Provisioning - API Server, etcd, and Scheduler Performance
Goal: Investigate why batch provisioning times degraded from 90s (batch 1) to 1,388s (batch 200) across the 10K VM run, identify the bottleneck components at each scale tier, and build a validated projection model.

Key Takeaways

  • Batch times grow sub-linearly following a power law: t = 0.65 × n0.844 (R² = 0.95)
  • The dominant bottleneck shifts from CDI/CSI cloning (0-2K) to etcd/API server (5K+)
  • etcd slow applies and object count have the strongest correlation with degradation (r > 0.92)
  • CSI memory scales linearly and is predictable from small tests. API server degradation is NOT.
  • At 20K VMs, batch times would reach ~2,760s (46 min) - still under the 3,600s timeout

Scale Tier Bottleneck Analysis

The degradation curve reveals four distinct performance tiers, each dominated by a different bottleneck.

Tier 1: 0-2K VMs (Fast Zone)

Avg batch time332s (5.5 min)
Primary bottleneckCDI/CSI cloning operations

Evidence: etcd DB/slow applies flat, API rate moderate, scheduler p99 briefly spikes to 30ms then drops. The 2x jump from batch 1 (90s) to batch 20 (181s) reflects CDI queue depth growth.

Tier 2: 2K-5K VMs (Transition Zone)

Avg batch time775s (12.9 min)
Primary bottlenecketcd transaction latency + API server LIST operations

Evidence: etcd p99 spikes to 598ms at 4K VMs, LIST pods p99 hits 920ms at 3K, object count grows 180K→246K. Compaction visible at 2K (DB drops from 2.3GB to 927MB then rebuilds).

Tier 3: 5K-7K VMs (Heavy Degradation)

Avg batch time1,010s (16.8 min)
Primary bottleneckAPI server watch event fanout + scheduler O(n) scaling

Evidence: Watch connections growing linearly, API rate plateaus at ~517 req/s (throughput ceiling), etcd slow applies +139.

Tier 4: 7K-10K VMs (Saturated Zone)

Avg batch time1,347s (22.5 min)
Primary bottleneckCompound saturation (etcd + API + scheduler + OVN)

Evidence: etcd slow applies rate 3x higher than Tier 3 (+618 vs +139), etcd p99 hits 796ms, object count 302K→367K, API rate 590→687 req/s (increasing load despite degradation).

Would Cooldown Pauses Between Batches Help?

Short answer: No.

The degradation is structural (driven by total object count), not transient (driven by burst rate).

Evidence from the 10K run:

  • Batch times at the same VM count are consistent regardless of preceding batch duration
  • No "recovery" pattern was observed after naturally longer batches
  • The degradation curve is monotonically increasing - pauses don't reduce it

What about etcd defrag pauses?

Unlike generic cooldowns, targeted etcd defragmentation at milestones (2K, 5K, 8K VMs) could help by compacting the database. The etcd DB grew from 927MB to 3.2GB during the run, and compaction events (visible at the 2K mark where DB dropped from 2.3GB to 927MB) temporarily improved performance.

Cooldown Overhead Comparison

CooldownAdded TimeNew TotalBenefit
0s (current)047h 30mFastest possible

Recommendation

Skip generic cooldowns. Instead, add etcd defragmentation triggers at 2K, 5K, and 8K VM milestones during provisioning. This addresses the root cause (DB bloat) rather than the symptom.

Recommendations

Each recommendation is backed by specific observations from the 10K run, with expected impact and rationale.

etcd Optimization

1. Run etcd defragmentation at provisioning milestones (2K, 5K, 8K VMs)

Why it helps: During the 10K run, etcd DB grew from 927MB to 3.2GB. Compaction events (like the one at 2K VMs where DB dropped from 2.3GB to 927MB) temporarily improved performance. Defrag reclaims disk space and reduces I/O pressure on the etcd WAL and snapshot files.

Impact: Low-Medium | Priority: High

Data: etcd DB size 927MB → 3,189MB over the run. Compaction at 2K VMs coincided with the best etcd p99 (199ms at 3K VMs).

Note: Maintenance-window defrag is good hygiene but won't help during provisioning. Inline defrag during the run is where the value is.

2. Monitor etcd_server_slow_apply_total as an early warning

Why it helps: Slow applies accelerated sharply in Tier 4 (7K-10K VMs): +618 slow applies vs +139 in Tier 3. When the rate exceeds ~100 slow applies per 1K VMs, etcd is under significant stress and per-batch times will increase. This metric gives you a leading indicator to pause or intervene before performance collapses.

Impact: Observability - no direct improvement, but gives early warning to pause or intervene | Priority: High

Data: Tier 3 (5K-7K): +139 slow applies. Tier 4 (7K-10K): +618 slow applies (4.4x acceleration).

3. Consider dedicated SSD / increased IOPS for etcd

Why it helps: etcd p99 latency reached 796ms at 9K VMs. etcd is extremely sensitive to disk I/O latency - every etcd transaction (reads, writes, compactions) goes through disk. Faster storage directly reduces transaction latency, which cascades to faster API server responses since every API write waits for etcd consensus.

Impact: Medium - Would reduce the etcd contribution to batch time (estimated 20-45% of total depending on tier) | Priority: Low

Data: etcd p99 rose from 398ms (baseline) to 796ms (9K VMs). At Tier 4, API/etcd contributed ~45% of batch time.

API Server Tuning

4. Increase --max-mutating-requests-inflight

Why it helps: We observed max 10 concurrent mutating requests during batch applies. The default limit is 200, but if it's been lowered, it could throttle batch creation. Each batch of 50 VMs generates ~250 API mutations (VM + VMI + DV + PVC + Pod), so a low limit would serialize these mutations and slow the batch.

Impact: Low - Only helps if the limit is actually being hit (we didn't see evidence of throttling) | Priority: Low

Data: Max 10 concurrent mutating requests observed. Need to verify current --max-mutating-requests-inflight setting on the cluster.

5. Enable API Priority and Fairness (APF) for VM operations

Why it helps: Without APF, VM creation requests compete with all other API traffic (monitoring, controllers, operators) in a single FIFO queue. APF lets you create a dedicated FlowSchema for VM provisioning, guaranteeing bandwidth for batch operations. This prevents starvation when the API server is loaded - especially important at Tier 3-4 where API rate reached 687 req/s.

Impact: Medium - Would stabilize batch times by preventing other workloads from competing with provisioning | Priority: Medium

Data: API request rate grew from 492 to 687 req/s. At Tier 3, API throughput plateaued at ~517 req/s - a sign of saturation where APF would help most.

6. Enable watch bookmarks to reduce watch event overhead

Why it helps: Watch connections grew from 22,115 to 22,705 during the run. Each new Kubernetes object triggers watch events to all active watchers. Watch bookmarks let watchers skip ahead to a known resource version without processing every intermediate event, reducing API server CPU spent on event serialization and fanout.

Impact: Medium - The API server spent increasing time on watch event processing as object count grew. Bookmarks reduce this overhead. | Priority: Medium

Data: 22,115 → 22,705 watch connections (+590). With 366K objects, each object change fans out to thousands of watchers.

Scheduler

7. Evaluate bin-packing scheduler profile

Why it helps: The default scheduler spreads pods across nodes, evaluating all feasible nodes for each pod. Bin-packing fills nodes sequentially, reducing the number of nodes the scheduler needs to score. With 39 worker nodes and 10K pods, bin-packing could significantly reduce scheduling time by evaluating fewer nodes per pod placement decision.

Impact: Medium - Scheduler p99 was relatively low (~8ms) but contributes ~20-25% of batch time through cumulative effect on 50 pods per batch. | Priority: Medium

Data: 39 worker nodes, 50 pods per batch. Default spread profile evaluates all 39 nodes per pod; bin-packing would typically evaluate 5-10.

Architecture Changes (for 20K+ Scale)

8. Namespace sharding - split VMs across multiple namespaces

Why it helps: LIST operations are scoped to namespace. With all 10K VMs in one namespace, every LIST pods/VMs query must scan all 10K+ objects. Splitting into 4-5 namespaces (2K VMs each) would reduce LIST latency by 4-5x. This directly addresses the dominant bottleneck in Tier 3-4, where API/etcd accounted for 40-45% of batch time.

Impact: High - This is the single most impactful change for scaling beyond 10K. LIST operations on pods/VMs were the primary API server bottleneck. | Priority: High

Data: Object count grew to 366,595. LIST latency correlates strongly with object count (r = 0.84). At 4-5 namespaces, each LIST scans ~2K VMs instead of 10K.

9. Run 2K and 5K VM checkpoints to recalibrate projections

Why it helps: The 1K preliminary tests couldn't predict the degradation beyond 2K VMs because the control plane was still in its "fast phase" (Tier 1). Running intermediate checkpoints captures the degradation curve early - specifically the Tier 1-to-2 transition at ~2K VMs - before committing to a 48-hour run.

Impact: No performance improvement, but prevents underestimating run duration by 6x (as happened with the 1K-to-10K projection) | Priority: High

Data: 1K batch time was 181s, suggesting ~10h total for 10K. Actual total was 47.5h - a 6x underestimate because the degradation curve wasn't visible at 1K.

10. Reduce objects per VM

Why it helps: Each VM creates ~5-6 Kubernetes objects (VM, VMI, DataVolume, PVC, PV, Pod). At 10K VMs that's ~60K objects. If any of these can be consolidated or eliminated (e.g., using pre-provisioned PVCs instead of DataVolume templates, or using VM pools), the total object count drops, directly reducing API server LIST latency, etcd transaction volume, and watch event fanout.

Impact: High - Object count had the strongest correlation with batch time degradation (Pearson r = 0.84). | Priority: Medium

Data: 366,595 objects at 10K VMs. Reducing from 6 to 4 objects per VM would cut ~20K objects, proportionally reducing LIST and watch overhead.
