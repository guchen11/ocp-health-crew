Hypothesis: The API server degradation observed in the 10K VM test is primarily driven by namespace-scoped LIST operations. If VMs are distributed across multiple namespaces, LIST latency should stay low and batch times should remain flat, eliminating the progressive slowdown seen in single-namespace provisioning.

Key Findings

  • Namespace sharding provides ~30% average improvement in the 1K-2K VM range, but the benefit erodes at higher scale
  • At 3K VMs, sharding provided no benefit - last batch was 572s vs baseline 543s
  • The dominant bottleneck is cluster-global (etcd, CSI clone operations), not namespace-scoped LIST operations
  • DV clone time is the growing component: 121s (batch 1) to 447s (batch 60), a 3.7x increase
  • VM boot time stays flat at ~15-30s regardless of scale (occasional spikes to 90-120s)
  • Sharding alone is NOT sufficient for eliminating degradation at 10K scale

DV Clone Time is the Bottleneck

The DV clone operation (CSI snapshot + restore) accounts for 84-91% of every batch's total time. This operation involves:

  • etcd transactions - creating PVC, PV, VolumeSnapshot, and DataVolume objects
  • CSI/Ceph clone - the actual block-level clone on the ODF storage backend
  • CDI controller - coordinating the clone workflow

Since DV clone time grows regardless of namespace distribution, the bottleneck is in the shared storage backend and etcd, not in namespace-scoped API operations.

Namespace sharding does reduce degradation in the 1K-2K VM range (~30% faster), confirming that namespace-scoped LIST operations contribute to the bottleneck. By 3K VMs, cluster-global bottlenecks (etcd transaction latency, CSI clone queue depth, total object count) dominate, and namespace sharding provides no measurable improvement.

Projection: Sharding at 10K Scale

Would 10 namespaces help at 10K?

Based on the 3K test data, sharding alone would provide marginal improvement at 10K scale. The DV clone time growth curve is driven by cluster-global factors, not namespace size. Extrapolating:

MetricBaseline (1 NS)Projected Sharded (10 NS)

A 10-15% overall improvement, saving ~5-8 hours on a 48-hour run. Meaningful, but not transformative.

Recommendations

1. Combine sharding with etcd defragmentation (next test)

A test script is ready (ns-sharding-defrag-test.sh) that runs the same 3K test but triggers etcd defrag at 1K and 2K milestones. In the original 10K run, etcd compaction at 2K VMs dropped the DB from 2.3GB to 927MB and coincided with the best etcd p99 latency (199ms). If defrag can reset the etcd performance penalty at each milestone, combined with sharding, batch times may stay substantially lower.

Expected outcome: If etcd DB bloat is a significant contributor to DV clone slowdown, defrag should produce a visible step-down in batch times after each milestone.

2. Keep namespace sharding as standard practice

Even though the benefit diminishes at scale, sharding provides:

  • 30% improvement in the 1K-2K range (the most common operating range)
  • Better operational isolation (failures in one namespace don't affect others)
  • Easier cleanup and management
  • No additional cost or complexity

3. If defrag doesn't help, investigate CSI/Ceph clone performance

DV clone time accounts for 85-95% of batch duration and is the component that grows. If etcd defrag doesn't reduce DV clone times, the bottleneck may be in the Ceph storage backend itself (OSD throughput, clone queue depth, or snapshot management overhead). This would require Ceph-level investigation with the storage team.

Root Cause: CDI Controller Orchestration Overhead

All evidence points to the CDI (Containerized Data Importer) controller as the primary bottleneck:

  • DV clone time = 85-97% of batch time and it grows with total VM count
  • Ceph is not slow - zero slow ops, <2% OSD utilization
  • etcd is not bloated - 536MB DB, defrag didn't help
  • Fresh namespaces don't help - batch 61 in a new empty namespace was 501s
  • CDI is a single pod managing all DataVolume lifecycle across all namespaces

As total DataVolume count grows, CDI must track more objects, make more API server calls for status updates, manage more snapshot/clone workflows, and coordinate with the CSI provisioner. This overhead scales with total cluster object count, not with namespace size or etcd DB size.

Updated Recommendations

1. Investigate CDI controller scaling options

The single CDI controller pod is the most likely bottleneck. Potential improvements:

  • CDI worker count tuning - check if CDI has configurable concurrency/worker settings
  • CDI controller resource limits - ensure it has sufficient CPU/memory
  • CDI version - check for performance improvements in newer versions
  • DataImportCron / pre-provisioned PVCs - bypass CDI clone pipeline entirely by pre-creating PVCs

2. Reduce objects per VM (high impact, original recommendation #10)

Each VM creates ~6 Kubernetes objects (VM, VMI, DV, PVC, PV, Pod). At 10K VMs that's 60K+ objects the CDI controller and API server must track. Reducing this - e.g., using pre-provisioned PVCs instead of DataVolume templates - would directly reduce CDI controller load and API server overhead.

3. Keep namespace sharding (marginal but free)

Sharding provides ~30% improvement in the 1K-2K range and better operational isolation. Worth keeping as a standard practice even though it doesn't solve the core bottleneck.

4. Reserve etcd defrag for 10K+ scale

At 3K-4K VMs, etcd DB is only ~536MB and defrag is not useful. At 10K VMs in the original test, the DB grew to 3.2GB - defrag at milestones may still be valuable at that scale. Test it during the next 10K run.
