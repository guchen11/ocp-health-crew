Background: Preliminary Batch Size Evaluation

Before the full 10K run, preliminary tests were conducted at small scale (up to 1,000 VMs) to determine the optimal batch size, resource configuration, and projected memory behavior. Four test phases were run, progressively narrowing the parameter space. The winning configuration (50 VMs/batch with performance-tuned ODF resources) was selected based on the best combination of throughput, low degradation, and manageable CSI memory growth.

CSI memory scales linearly with VM count, making it predictable from small-scale tests. However, the time projection (~8 hours) was significantly off (actual: 47h 30m) because cluster control plane performance degrades progressively beyond ~2K VMs - as object count grows, the API server, scheduler, and etcd database take progressively longer to process each request - a pattern not visible from 1K-VM tests.

Why CSI was accurate but time was not:

CSI memory scales linearly with VM count - each VM adds a roughly constant amount of metadata to the CSI plugin regardless of how many other VMs exist. This makes it highly predictable from small-scale tests. The 1K-test growth rate of ~0.095Mi/VM extrapolated to ~1.6Gi at 10K, and the actual peak was ~1,532Mi.

Cluster control plane performance degrades progressively with VM count - each new VM adds objects that increase API server response times, etcd transaction latency, and scheduler evaluation time. At 1K VMs the cluster handles requests efficiently, but beyond ~2K VMs, this compounding effect becomes significant. This was not visible from 1K-VM tests and could not be predicted from small-scale data. The result: a 6x time overrun versus the linear projection.
