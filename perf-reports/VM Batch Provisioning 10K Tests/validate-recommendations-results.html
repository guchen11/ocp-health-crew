Detailed Findings per Recommendation

1. Inline etcd Defrag at Milestones - NOT NEEDED

Tested in: Namespace sharding 3K test (2026-06-08)

Finding: At 3K VMs, etcd DB was only 536MB. Defrag recovered 21MB (4%) and had zero effect on batch times. Post-defrag batches were 496s vs 458s pre-defrag - slightly worse due to continued CDI-driven degradation.

With PVC bypass at 10K: etcd DB is 1,206MB (vs 3,189MB with CDI at 10K). PVC bypass creates fewer objects per VM, so the etcd DB grows slower. Defrag would reclaim minimal space and have no effect on batch times (which are already flat at 83s).

Verdict: Not needed with PVC bypass. May still be useful for CDI-based provisioning at 10K+ scale where DB reached 3.2GB.

Verdict: Not needed for PVC bypass. Could be a preventive measure for CDI workloads at higher scales, but data shows no current throttling.

7. Bin-packing Scheduler - NICE-TO-HAVE

Current profile: Default (LowNodeUtilization - spread across nodes)

VM startup analysis from PVC bypass 10K test:

MetricValue
Median VM startup time (per batch)44s
Best VM startup time37s
Worst VM startup time (spike)167s
Spike frequency~1 in 7 batches
Total VM time (200 batches)~11,200s
If all batches had best VM time (37s)~7,400s (saving ~63 min)

Analysis: The VM startup spikes (~1 in 7 batches) are the main source of batch time variance. However, these appear to be caused by the virt-controller processing burst of VirtualMachine objects, not by scheduler node scoring. The scheduler p99 latency was ~8ms in the original test - milliseconds per pod. Bin-packing would reduce the number of nodes scored but wouldn't affect the virt-launcher pod creation time.

Potential savings: If bin-packing eliminated all spikes (unlikely), it would save ~63 minutes over the 10K run (~19% of total). More realistically, 10-15 minutes savings.

Verdict: Nice-to-have. The spikes are not caused by scheduling but by virt-controller burst processing. Bin-packing might reduce variance marginally but won't address the root cause of spikes.

Action Required: CSI rbdplugin Memory Limit

The CSI rbdplugin-ctrlplugin pod is running at 939Mi out of its 1Gi limit (94% utilization). This is dangerously close to OOM. With 10K VMs and their PVCs attached, the CSI plugin must track all volume attachments in memory.
