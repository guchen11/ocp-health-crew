Evidence 5: Source Code Comparison (CDI v1.57 vs v1.60)

Compared the upstream CDI source code between v1.57.1 (CNV 4.19) and v1.60.5 (CNV 4.22):

Key architectural change introduced in CDI v1.59.0 (CNV 4.21):

Two PRs transformed the CDI API server from a lean webhook handler into a heavier process:

  1. PR #2813 - "Add PVC spec mutating webhook rendering based on StorageProfiles"
    • Added cluster.New(cfg) + cluster.Start(ctx) - starts a full controller-runtime cluster with informers and caches inside the API server
    • Added CreateAvailablePersistentVolumeIndex() - field indexers for PVs
    • Added new PVC mutating webhook (pvc-mutate)
    • Registered schemes for CoreV1, CDI, VolumeSnapshots
  2. PR #3029 - "Feature Gate and annotation for PVCs to be adopted by DataVolumes"
    • Added ClaimMayExistBeforeDataVolume() to the validate webhook
    • This reads CDIConfig via controller-runtime client on every validation to check feature gates
    • Added controllerRuntimeClient dependency to the validation webhook

In CDI v1.57 (CNV 4.19): The API server was a lightweight process with only direct k8s API clients. No informers, no caches, no field indexes. The webhook handlers made direct API calls only when needed.

In CDI v1.59+ (CNV 4.21+): The API server now runs a full controller-runtime cluster alongside webhook handling. Under concurrent load, the informers, caches, and event processing compete with webhook requests for CPU/memory on the single-replica pod.

Ironically, the validate webhook actually does fewer API calls in v1.60 than v1.57 (PR #3331 removed source PVC/snapshot validation from the webhook). But the infrastructure overhead of the embedded controller-runtime cluster more than offsets this improvement.

Root Cause (Refined)

The regression has two contributing factors:

  1. Architectural change (v1.59/CNV 4.21): Adding a controller-runtime cluster inside the single-replica CDI API server increased its resource footprint and added background work competing with webhook handling
  2. Operational limitation: The CDI operator hardcodes the API server to 1 replica with only 100m CPU request. This was tolerable in v1.57 (lean webhook handler) but insufficient for v1.59+ (heavier process)

Recommended Fixes

  1. Immediate: Allow CDI API server replica count to be configurable (currently hardcoded to 1 by the CDI operator). 2 replicas halved the P50 webhook latency.
  2. Short-term: Increase default CPU request from 100m to at least 500m, or add an HPA.
  3. Medium-term: Move the controller-runtime cluster out of the API server process, or make it lazy-load only when the WebhookPvcRendering feature gate is enabled.
  4. Long-term: Re-evaluate whether the SubjectAccessReview in the mutate webhook can be cached or batched.
