CNV-95003: VM Creation Performance Regression - Root Cause Analysis

Lab: clod30 (aa37-h07-000-r740xd.rdu3.labs.perfscale.redhat.com)
OCP: 4.22.6 | CNV: 4.22.2 (CDI v1.60.x) | ODF: 4.22.1
Date: Aug 13, 2026

TL;DR

The CDI API server (cdi-apiserver) was designed as a lightweight webhook handler. In CDI v1.59 (CNV 4.21), two PRs (#2813, #3029) added a full controller-runtime engine (informers, caches, field indexers) inside this same single-replica pod running on only 100m CPU. The background work now competes with webhook handling for CPU.

This is one root cause with two symptoms:

  • Single VM: ~30-50% slower per VM creation. The webhook now shares CPU with controller-runtime background work, adding ~45ms overhead to every call (125ms measured vs ~80ms expected baseline). This matches the regression Purti reported in the original CNV-95003.
  • At scale (100+ VMs): Up to 19x slower at P99. Concurrent webhook requests queue up on the overloaded single-replica pod, compounding the per-request overhead.

Component: CDI (containerized-data-importer), specifically the cdi-apiserver deployment.
Regression introduced in: CDI v1.59.0 / CNV 4.21 (not present in CDI v1.57 / CNV 4.19).

Evidence 5: Source Code Comparison (CDI v1.57 vs v1.60)

Compared upstream CDI source between v1.57.1 (CNV 4.19) and v1.60.5 (CNV 4.22).

Key architectural change introduced in CDI v1.59.0 (CNV 4.21):

Two PRs transformed the CDI API server from a lean webhook handler into a heavier process:

  1. PR #2813 - "Add PVC spec mutating webhook rendering based on StorageProfiles"
    • Added cluster.New(cfg) + cluster.Start(ctx) - starts a full controller-runtime cluster with informers and caches inside the API server
    • Added CreateAvailablePersistentVolumeIndex() - field indexers for PVs
    • Added new PVC mutating webhook (pvc-mutate)
  2. PR #3029 - "Feature Gate and annotation for PVCs to be adopted by DataVolumes"
    • Added ClaimMayExistBeforeDataVolume() to the validate webhook
    • Reads CDIConfig via controller-runtime client on every validation to check feature gates

CDI v1.57 (CNV 4.19): Lightweight process with only direct k8s API clients. No informers, no caches, no field indexes.

CDI v1.59+ (CNV 4.21+): Runs a full controller-runtime cluster alongside webhook handling. Under concurrent load, informers, caches, and event processing compete with webhook requests on the single-replica pod.

Ironically, the validate webhook does fewer API calls in v1.60 than v1.57 (PR #3331 removed source validation). But the infrastructure overhead more than offsets this.

Root Cause

One root cause, two symptoms. In CDI v1.59 (CNV 4.21), a controller-runtime engine was added inside the CDI API server - a single-replica pod with 100m CPU that was designed to only serve webhooks. The background work (informers, caches, indexers) now competes with webhook handling for CPU:

  • Single VM (30-50% slower): Every webhook call pays ~45ms overhead from CPU contention with background work, even with no other load.
  • At scale (up to 19x slower at P99): Concurrent requests queue on the overloaded pod, compounding the per-request overhead.

Recommended Fixes

  1. Immediate: Allow CDI API server replica count to be configurable (currently hardcoded to 1 by the CDI operator). Our test showed 2 replicas halved the P50 webhook latency and gave 4x more VMs running at 60s.
  2. Short-term: Increase default CPU request from 100m to at least 500m, or add an HPA.
  3. Medium-term: Move the controller-runtime cluster out of the API server process, or lazy-load it only when the WebhookPvcRendering feature gate is enabled.
