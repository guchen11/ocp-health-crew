Test Design

Two identical tests creating 100 VMs from the same Ceph RBD snapshot on the same cluster, same time window. The only difference: whether CDI (DataVolume API) is in the path or not.

  • Test A (WITH CDI): VMs created with DataVolume templates - CDI mutating + validating webhooks fire for every DV
  • Test B (WITHOUT CDI): PVCs created directly from VolumeSnapshot (native K8s), then VMs attached to pre-bound PVCs - no CDI webhooks involved

Root Cause Confirmed

The CDI admission webhooks (datavolume-mutate and datavolume-validate) are adding ~4.8 seconds of latency per DataVolume (2.44s mutate + 2.34s validate). This is the primary bottleneck.

When CDI is bypassed (Test B), VMs reach Running state 2.67x faster. The CDI API server runs as a single replica, creating a serialization point that compounds under load.

KubeVirt's own webhooks are fast (~5-14ms each), and Ceph RBD snapshot cloning is also fast (~300ms per clone as measured in our earlier DV-only isolation test). The bottleneck is specifically in CDI's webhook processing.

Conclusion

  • CDI webhook latency is the confirmed root cause of the VM creation performance degradation reported in CNV-95003
  • This is reproducible on OCP 4.22.6 / CNV 4.22.2 without needing Fusion HCI - it's a CDI code issue, not infrastructure
  • The regression adds ~4.8s per VM through webhook overhead alone, with compounding effects at scale due to the single-replica CDI API server
  • No existing Jira bug covers this specific CDI webhook latency regression (CNV-90050 is related but focuses on different CDI throughput aspects)

Recommended Next Steps

  1. File a dedicated Jira bug for CDI webhook latency regression
  2. Investigate what changed in CDI 4.22 webhook handlers (mutate/validate) that increased latency from expected sub-50ms to 2.4s
  3. Consider scaling CDI API server beyond 1 replica to reduce serialization
  4. Test with CDI 4.19/4.20 to identify exact regression point
